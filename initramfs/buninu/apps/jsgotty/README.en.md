## Intro
- Expose your terminal through browsers, CLI clients, and modern web protocols.
- This is a GoTTY-compatible server rewritten in JavaScript / Bun.
- It is based on the original GoTTY code, with most of the new code generated by Codex.
- It includes a frontend and WebTTY protocol implementation adjusted for `jsgotty`.
- Original repository:
- https://github.com/sorenisanerd/gotty
- .
- Keywords: Terminal, TTY, Browser, CLI Client, Session management, Kitty graphics protocol, ZMODEM

### Features
- Resumable reconnect: after the browser disconnects, you can reconnect to the original shell / PTY with a reconnect token instead of spawning a new shell.
  * jsgotty supports two connection modes: normal mode and session mode.
  * Use `--reconnect` or `--session` to enable session mode.
  * See the detailed mode explanation below.
- Kitty Graphics Protocol: displays inline terminal images.
  * For example, `bun viu.mjs 1.png` shows an image directly in the terminal.
  * Set `JSGOTTY_KITTY_DEBUG=1` to write the Kitty image debug log.
  * Windows does not use Kitty protocol; it uses a custom protocol.
- ZMODEM / `rz/sz`: select files in the browser and upload them to the remote shell.
  * You can also download files from the remote shell.
  * Windows does not use ZMODEM; it uses a custom protocol.
  * Linux has been tested with uploads/downloads around an 80MB Bun binary.

```sh
bun gotty.js -w bash
```

### CLI Client

- `client.mjs` is an interactive terminal client that connects directly to GoTTY.
- Basic connections are compatible with Golang GoTTY.
- Session listing, writer management, and remote PTY termination require this project's jsgotty server.
- See the detailed mode explanation below for the difference between normal mode and session mode.

#### Basic connection

```sh
# Connect to the default ws://127.0.0.1:8080/ws
bun gotty.js --client

# Connect to 127.0.0.1:8081
bun gotty.js --client 8081

# HTTP(S) page URLs and WS(S) URLs are accepted
bun gotty.js --client https://example.com/terminal/

# Connect with credentials
bun gotty.js --client -c user:pass 8081
```

#### Session management

```sh
# List current sessions
bun gotty.js --client -ls [target]

# Resume an existing session by reconnect token or PID
# Requires session mode
bun gotty.js --client -r <token|pid> [target]

# Disconnect the current writer while keeping the PTY session alive
# Requires session mode
bun gotty.js --client -d <token|pid> [target]

# Terminate the matching PTY session
bun gotty.js --client -k <token|pid> [target]
```

The first argument can also use subcommand aliases:

- `ls`, `list`, `list-sessions` => `-ls`
- `attach`, `a <token|pid>` => `-r <token|pid>`
- `detach <token|pid>` => `-d <token|pid>`
- `kill-session`, `stop <token|pid>` => `-k <token|pid>`

- `-ls` reads the server's `/css.md` session list.
- Open `/css` to view the session list in a browser.
- If `/css` shows a static file list instead of sessions, the server is Golang GoTTY, not jsgotty.
- `-r` requires session mode; it resumes the matching PTY session.
- `-d` requires session mode; after disconnecting the session writer, the session remains alive and the next writable client can take over.
- `-k` terminates the matching PTY/session.
- `--arg <value>` may be repeated to pass command arguments; `--arguments <query>` passes a raw query string.
- `--cols` and `--rows` set the initial terminal size.
- `GOTTY_CREDENTIAL` and `GOTTY_RECONNECT_TOKEN` may be used to configure credentials and the reconnect token.
- See "Normal Mode / Session Mode" below for PTY creation, writer/viewer roles, and reconnect retention behavior.
- Golang GoTTY does not support the jsgotty control protocols used by `-ls`, `-r`, `-d`, and `-k`.

## Normal Mode / Session Mode

The `jsgotty` server has two connection modes:

- Normal mode: no `--reconnect` or `--session`
- Session mode: `--reconnect` or `--session`

### Normal Mode

- Each new browser or `client.mjs` connection creates a new `PtySession` and a new PTY.
- Two clients connected at the same time are usually two different shells / PTYs. They do not share screen output, input, or process state.
- When a client disconnects, its corresponding PTY session is closed.
- If the browser window, tab, or websocket closes normally, the server cleans up the PTY for that connection.
- Normal mode cannot resume an existing PTY. If the browser or CLI sends a reconnect token / PID, it will not resume the old session and will create a new PTY instead.
- `/css` and `/css.md` still list active session PIDs and command names, but they do not provide reconnect tokens or reconnect links.
- `client.mjs -ls` can list sessions; `-k <pid>` can terminate a session by PID; `-r` and `-d` require session mode.

### Session Mode

- Enable it with `--reconnect` or `--session`.
- The first connection creates a new `PtySession` and PTY unless it provides a resumable token / PID.
- The server generates a reconnect token for each session and sends the session PID and token to the frontend.
- Later, a browser or CLI can use the reconnect token or PID to resume the same PTY instead of spawning a new shell.
- Multiple clients can connect to the same PTY session.
- The first writable client becomes the writer and can send keyboard input, resize events, ZMODEM controls, and other data to the PTY.
- Other clients are viewers. They receive terminal output but do not write to the PTY.
- A client can also use `--readonly` to connect explicitly as a viewer.
- If the writer disconnects while the session still has viewers, existing viewers are not automatically promoted to writer. The next writable client that resumes the same session can become the new writer.
- After the last client disconnects, `--reconnect-time` decides whether the PTY is kept.

#### `--reconnect-time` Behavior
- `> 0`: keep the PTY for the specified number of seconds after the last client disconnects. It can be resumed during that window; after timeout, the PTY is closed.
- `= 0`: close the PTY immediately after the last client disconnects.
- `< 0`: keep the PTY indefinitely until the shell exits, `-k` terminates it, or the server stops.

#### Frontend Reconnect Behavior
- When `reconnect-time > 0`, the frontend retries automatically several times within the timeout.
- When `reconnect-time < 0`, the frontend retries once per minute.
- On disconnect, the overlay provides a `Reconnect` button for immediate manual retry.
- Right-click / long-press on that button lets you enter a custom reconnect token or PID.

## Kitty keyboard

The web terminal supports the shortcut-related parts of the [Kitty keyboard protocol](https://sw.kovidgoyal.net/kitty/keyboard-protocol/), separately from Kitty graphics. Legacy keyboard encoding remains the default. A terminal application can opt in:

```sh
printf '\033[>11u'  # 1: disambiguation + 2: repeat/release + 8: all keys
printf '\033[<u'    # restore the previous mode when the application exits
```

The receiving application must decode these sequences and restore the mode in its exit/finally handler; do not leave an ordinary shell in this mode. Negotiation supports `CSI ? u`, `CSI = flags ; mode u`, push and pop. Normal and alternate screens have independent stacks, limited to 32 entries. Reconnection, full reset and soft reset clear the state. Use flag `1` for unambiguous shortcuts, or `11` for modifier keys and press/repeat/release reporting.

DOM Meta maps to Kitty **Super (bit 8)**, not the separate Meta bit (32). Super+X is `CSI 120;9u`; Ctrl+Shift+Super+X is `CSI 120;14u`. Release events add `:3` when enabled.

Supported flags are **1, 2 and 8**; alternate keys (4) and associated text (16) are not implemented or reflected in the negotiated flags. IME composition/text commits and paste retain their existing paths; physical keys and releases cannot be inferred from committed text. Letters, digits, punctuation, navigation, Tab/Enter, function keys, keypad keys and standard Kitty media keys retain distinct modifiers. OS/browser-reserved shortcuts may never reach the page. Keys without standard Kitty codes, such as brightness and microphone mute, are not assigned private encodings.

This implements **jsgotty → PTY** encoding. Controlling Hyprland/Omarchy still requires Casty or another receiver to enable/decode Kitty keyboard and forward Super and release events. It does not complete the remote desktop input chain or change the mouse protocol.

Reload the jsgotty page after updating. Run the manual tester inside its terminal:

```sh
bun tests/manual/kitty-keyboard.js
```

It prints negotiated flags, raw sequences, modifiers and event types, exits after 60 seconds or unmodified Escape/q/Ctrl-C, and restores the previous keyboard/raw modes. An optional real bundled-xterm test uses an already installed browser:

```sh
CHROMIUM_HEADLESS=/path/to/chromium-headless-shell node --test tests/kitty-keyboard-browser.test.js
```

## Android Keyboards

For Android WebViews that deliver Meta down/up but lose `metaKey`, jsgotty tracks both Meta keys inside its own input handler. Blur or page hiding clears held state and sends releases for reported keys when event reporting is enabled.

In the Android terminal, Alt with letters, digits, punctuation, or space sends terminal Alt sequences based on physical key positions (US layout, including Shift), bypassing accent dead-key handling. Alt-E/I/N/U therefore no longer compose characters such as é, ê, ñ, and ü; input methods and paste remain available. When WebView omits `code`, recognized legacy `keyCode` values provide a fallback. Dead keys delivered only as `keyup` send the shortcut on release, without duplicating a previously handled `keydown`. Active composition, Ctrl, Meta, AltGr, and unidentified keys retain their existing handling. This applies only inside the jsgotty terminal and does not modify Android system keyboard settings.

## Current implementation
- Uses Node's built-in `http` / `https`
- Uses `ws` for WebSocket upgrade handling
- Uses bundled frontend assets in `./static`, including kitty overlay and WebTTY / ZMODEM frontend logic
- Supports inline terminal images
- Supports file upload / download

### PTY backends
- Linux / macOS: use Bun's built-in PTY via `Bun.spawn(..., { terminal: ... })`
- Windows: use patched `node-pty`, while still launching `gotty.js` through `bun`
  * Bun versions >= 1.3.14 use Bun's built-in PTY

### Kitty intro
- If the terminal program outputs images using Kitty Graphics Protocol on Linux, the frontend displays those images at the corresponding terminal position.
- Windows uses a custom protocol.
- Usage:

```sh
bun viu.mjs 1.png
# or bun gotty.js --viu 1.png
```

### rz upload intro
- When the remote shell runs:

```sh
bun rz.js
# or bun gotty.js --rz
```

- The frontend opens a file picker. After selecting files, they are uploaded to the current shell directory using ZMODEM.

### sz download intro
- When the remote shell runs:

```sh
bun sz.js file.txt
# or bun gotty.js --sz file.txt
```

- The frontend receives the ZMODEM download data and lets the browser download the file.

## Notes
- The goal is to emulate the main behavior of the original GoTTY and add additional features.
- Bun is the primary runtime.
- On Linux / macOS, PTY support will not work unless the program is launched with Bun.
- GoTTY config file loading is not implemented yet.
